# Agent C 后端 / 部署优化需求交接清单

> 日期：2026-11-12　依据：第一阶段《前端现状审计报告》（前端工作树 ignored 证据目录，未入库）+ 8180 运行契约实测
> 契约基线：`0.2.2-api-candidate`，**22 路径**，`HTTPBearer`；前端 `MISSING_CAPABILITIES` 已标注 8 组不支持能力。
> 性质：**需求清单**，前端不自行实现、不伪造接口、不在页面模拟写入成功。本轮未改后端、未重建镜像、未重启 8180、未动数据库。

## 0. 一句话结论

前端七个页面的主体业务交互（上传、创建任务、恢复/取消、下载、检索、原文预览等）**已接真实 API**；剩下的阻塞项集中在三类：① 后端契约确实缺 HTTP 接口（审核写入、入库批次/发布回滚、日志）；② 契约字段/响应语义不足，导致前端无法显示真实进度、无法稳定区分 401/403；③ 部署链路上前端产物固化在镜像里，前端任何修复都必须等镜像更新才能反映到 8180。

## 2. A 类：需新增的 HTTP 接口

| 优先级 | 缺失接口 | 页面 / 业务动作 | 前端现状 | 建议参数与要求 |
|---|---|---|---|---|
| **P0** | `POST /api/review/{parse_id}/approve`、`/reject`、`/mark-error`、`/save-revision` | 审核中心：审核通过 / 退回重解析 / 标记识别错误 / 保存人工修订 | 四按钮 `disabled`，`REVIEW_WRITE_AVAILABLE=false`，`review_write_supported` 恒 false，明确标注「待后端支持」 | `parse_id`、审核意见、修订内容、操作人与时间留痕；需 owner 隔离、幂等、失败返回明确错误码；`save-revision` 必须说明是覆盖还是生成新版本 |
| **P1** | `POST /api/ingestion/batches`、`/precheck`、`GET /api/ingestion/version-check` | 入库管理：发起批次、批次详情、各阶段成功/失败数、失败原因、版本校验 | 页面用「能力缺口表格」说明，无假批次、无假进度 | 批次标识、来源 `task_id`/`parse_id` 列表、阶段统计、失败明细、分页；**不得改变 PostgreSQL 结构或入库业务逻辑**（任务书明令） |
| **P1** | `POST /api/ingestion/publish`、`/rollback` | 入库管理：ACTIVE 发布与回滚 | `disabled`，public 无 ACTIVE 版本 | `kb_version`、授权凭据、回滚目标版本；需可审计、可失败回滚；发布后检索才可能不再是 `unpublished` |
| **P1** | `GET /api/parse/tasks/{task_id}/logs` | 解析中心：结构化阶段日志 | 日志抽屉只展示 `public(task)` 真实字段，不虚构阶段事件 | `task_id`、分页、时间范围；需区分阶段、耗时、成功/失败 |
| **P1** | `GET /api/system/resources`、`/api-logs`、`/error-logs`、`/audit-logs` | 系统监控：资源监控与三类日志 | 相关卡片为「未接入」静态空态 | 时间范围、分页、等级筛选；注意脱敏，不返回凭证 |
| **P2** | `SearchRequest` 扩展 `kb_version` / `issuing_authority` / `effective_status` | 法规检索：版本 / 发布机关 / 生效状态筛选 | 三个筛选器已移除并说明原因；请求体严格 `{query,mode,limit}` | 需在 **契约层**新增字段并放宽 422 校验；返回结构同时提供法规来源、版本、效力日期等可靠字段，否则前端不得推断展示 |
| **P2** | `GET /api/documents` 增加 `date_from` / `date_to` / `sort_by` / `order` | 文档管理：时间区间与任意排序 | 页面已明确不提供，也不多发字段 | 需与现有 `page/page_size/keyword/status/doc_type` 兼容，额外字段不得 422 |
| **P2** | 首页六项已移除指标的数据源 | 首页统计扩展 | 页面明确「需后端补齐接口后方可恢复」 | 需先定义清晰统计口径，避免把 uploads / tasks / parsed_documents 混为一谈 |

**验收要求（每个接口）**：OpenAPI 中给出路径、请求/响应 schema、错误码、认证要求、分页规则与 owner 隔离；写操作必须能在隔离测试数据上完成，且失败时前端能显示真实错误而非成功提示。

## 3. B 类：契约字段与响应语义增强（不改业务逻辑）

| # | 问题 | 建议 |
|---|---|---|
| B-1 | `review_write_supported` 恒为 `false` | 新增审核写入接口后，该字段应随运行期能力翻转；前端将把硬编码 `REVIEW_WRITE_AVAILABLE=false` 改为运行期契约探测，避免「源码已交付」被误判为「服务已加载」 |
| B-2 | 401 / 403 无可稳定区分的响应结构 | 明确 401 = 凭证无效/缺失、403 = 跨 owner 无权，并给出可区分字段；前端目前把两者合并为 `no-permission`，只能靠 hint 文案区分 |
| B-3 | `StatsResponse` 无 `list` 字段，字段缺失时前端 `defaultEmpty` 恒判 ready | DB 不可用请固定返回 `available=false` + 明确原因，避免前端把错误显示成 `0`（前端侧也会同步修 `?? 0`） |
| B-4 | 任务不返回总工作量 / 当前阶段 | 提供 `total_steps` / `current_step` / `progress`，前端才能展示真实进度；当前后端不给时前端坚持不显示模拟百分比 |
| B-5 | health 的模型类组件（paddle_ocr / pp_structure / bge_m3 / mineru）只有 UNKNOWN / NOT_CONFIGURED | 若要页面显示「正常」，需提供真实探活端点；否则前端只能保持「未知」，**不得把未检测组件显示为正常** |
| B-6 | `info.version = 0.2.2-api-candidate`，文档中契约名为 `frontend-api-v0.2.2-1` | 正式发布后统一版本口径，避免前端契约探测与交付文档互相矛盾 |

## 7. 建议顺序与硬边界

1. **P0 审核写入**：这是审核中心从「可读不可写」变为业务闭环的唯一阻塞项，优先给契约定义与隔离验证结果。
2. **P1 入库批次 / 发布回滚 / 日志**：先给只读查询（批次、记录、日志），再给写操作，便于前端分阶段接入。
3. **B 类契约语义**：与 A 类同批更新 OpenAPI，避免前端靠硬编码猜能力。
4. **C-1/C-2 镜像流程**：与下一次正式镜像更新一起带入，不要为改一句文案单独重启 8180。
5. **P2 筛选与高级查询**：待 ACTIVE 数据和检索链路可用后再评估。

**禁止事项**：不修改 PostgreSQL 数据结构或入库业务逻辑；不绕过 owner 权限隔离；不在前端伪造写入成功；不擅自改数据库、上传目录、模型与历史数据；不重建 v0.2.2 已验收镜像用于开发调试；不重启/替换当前正式 8180 容器；不把已停止的 8181 重新认定为入口。
