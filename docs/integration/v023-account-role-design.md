# v0.2.3 账号密码与角色方案（draft-4）

日期：2026-11-12，Asia/Shanghai。本版按用户最新决定，**ADMIN 拥有全部业务权限**。该决定覆盖 draft-2 中“ADMIN 不自动获得审核权”的旧设计；原有冻结 QA 结论仍仅适用于原镜像。

## 角色矩阵

| 功能 | USER 普通用户 | REVIEWER 审核员 | ADMIN 管理员 |
|---|---|---|---|
| 本人上传、解析任务与原件 | 本人 owner | 有个人 owner 时操作本人数据 | 全部 owner；可显式选择目标 owner |
| 审核详情与原件对照 | 本人数据只读 | 本人及明确授权的审核范围 | 全部数据 |
| 通过、退回、标错、修订 | 403 | review_owner_scopes 内 | 全部 owner |
| 文档软删除 | 403 | 403 | 全部 owner，仍受证据链保护 |
| 候选构建、发布和回滚 | 403 | 403 | 允许，仍须服务配置、审核与质量门禁 |
| 账号创建、角色/范围配置、停用、重置密码 | 403 | 403 | 允许 |
| API/错误日志 | 本人请求 | 本人请求 | 全部请求，包括未确认身份的请求元数据 |
| 审核审计 | 本人数据 | 授权范围 | 全部 |
| 已发布知识库查询 | 已认证可读 | 已认证可读 | 已认证可读 |

管理员全权限不跳过活动任务保护、原始证据保护、质量检查、乐观锁、不可变审核历史和独立部署审批。数据库 root、Docker 运维身份与应用 ADMIN 仍是不同概念。

## 身份与数据归属

- principal_id：不可由业务请求伪造的实际登录身份；新账号由服务端生成独立标识。
- owner_id：业务数据归属，与操作者分开记录；账号创建时 USER/ADMIN 未指定则生成独立 owner，纯 REVIEWER 可为空。
- roles：USER、REVIEWER、ADMIN，可组合；包含 ADMIN 即具有全部业务权限。
- review_owner_scopes：仅约束普通审核员，空列表不产生审核写权限，不接受通配符。
- credential_status：active、disabled、revoked；后两者不能继续认证。
- permissions、data_scope：GET /api/auth/me 和登录响应提供的服务端权限口径；ADMIN 为 data_scope=all。

ADMIN 的全局范围由服务端角色产生，不在配置或请求中使用 `*` 假装某个 owner。历史 local-user 保留普通 USER，不自动升级管理员或审核员，也不改历史 owner。

账号用户名大小写不敏感且唯一。不同普通用户不共享个人 owner。新账号不得占用已配置独立 Token 的 principal 或普通用户 owner；历史凭证迁移需明确处理原凭证，不能偷偷把历史 QA/共享 owner 归给新人。

账号 principal_id、用户名和既有 owner 不通过 PATCH 修改。修改审核范围、角色、状态、密码会记录 before/after 审计；密码及密码哈希不进入审计内容。

## 密码与会话

沿用 Bearer API，无公开注册。密码创建/重置要求 12–256 个字符；服务端保存 PBKDF2-SHA256、随机盐、600000 次迭代的哈希，不保存或回显明文密码。登录不会 trim 密码。

POST /api/auth/login 返回随机 opaque Bearer、expires_in=3600 和服务端 Principal。响应禁止缓存。会话文件仅保存 Token 摘要，原始 Token 不落盘、不入日志。每次 API 重新读取账号状态和角色，因此：

- 停用/撤销账号、重置密码后，旧会话下一请求 401。
- 撤销审核角色后，下一次审核写入 403；越界对象仍为 404。
- 退出登录标记当前会话撤销；一小时到期后重新登录。
- 用户名不存在和密码错误统一 401 invalid_credentials，不提供账号枚举提示。
- 登录限流：每个账号名 8 次/5 分钟，每个客户端 100 次/5 分钟，超限 429。

原有独立 Token 兼容保留，不生成默认管理员 Token。旧 Token 不能通过会话退出接口作全局撤销，返回 409，需在私密认证配置中停用；前端可清除本机会话但不能宣称旧凭证已经从服务端撤销。

## 持久化与初始化

复用私密认证配置文件和既有状态挂载，不增加第四套数据库。SQLite 仍存解析任务，PostgreSQL 仍存原解析及知识库，MySQL 仍存审核事件和修订。账号变更与账号审计通过文件锁和一次原子替换共同提交；最后一个有效管理员不能被误停用。

AUTH_ACCOUNTS_FILE 指向私密账号文件。配置目录须可写，使用目录挂载以支持原子替换，不能把单个只读文件当作可编辑账号库。账号文件、会话和日志必须保留在持久状态中并排除 Git。

首个管理员使用本机交互工具：

```text
python -m scripts.provision_auth_accounts --output local/private-auth/accounts.json --username your-admin-name
```

密码在本机两次不回显输入，不接收命令行密码参数；无默认密码。工具检查 Git 忽略规则并拒绝覆盖已有文件。本轮仅初始化过合成临时账号，未创建正式登录账号或注入正式 runtime。

配置账号文件后可将旧 Token 映射设为空 JSON 对象，使用纯密码登录模式；未配置账号文件且没有旧凭证时仍拒绝启动认证配置，不能匿名进入。运行配置仍由本地私密流程提供，不把配置、Token、DSN 或密码交给前端。

知识库写入另用可选私密 KNOWLEDGE_WRITE_PG_DSN，缺少时写接口 503；不借用解析存储凭证静默开启知识库写入。正式配置、账号初始化和 8180 切换仍须按批准流程执行。
