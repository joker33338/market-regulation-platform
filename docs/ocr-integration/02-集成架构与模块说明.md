# 集成架构与模块说明

## 设计

沿用项目 qa_core 分层，新增 qa_core/document_parsing，不搬入历史项目全部在线栈或数据库治理模块。

统一入口 DocumentParser.parse / parse_batch：
- Word：优先现有原生解析，表格用 OOXML 顺序结构提取，不调用 OCR。
- PDF：按页检查文本覆盖、图片区域、原生表格和列布局。可信文本优先原生提取；扫描页调用 OCR；复杂页采用 Structure。原生表格可提取时保留行列数据；混合文件逐页选择。
- 图片：auto 默认 OCR；人工指定 structure 时进行版面解析。
- 手工指定 auto / ocr / structure；表格模型单独启用，基础 profile 不加载表格、公式、印章、图表或矫正模型。

解析结果为 DocumentResult + PageResult，包含文件身份、原文、规范文本、Markdown、版面块、表格、置信度、来源定位、状态、耗时及原始引擎 JSON。原文与规范文本分离；表格 HTML、单元格与 spans 保留，不能把表格偷偷摊平成普通法条。

## 模型与运行时

固定使用 PaddleOCR 3.3.2 / PaddleX 3.3.10 / PaddlePaddle CPU 3.2.2 的已检查 API，不使用历史 2.x 参数。
模型目录明确配置，缺失项在引擎 import 前检查。CPU 为默认设备；模型只在首个相关解析请求时加载。

Windows 默认在一个持久化子进程内运行 Paddle：
1. 隔离 Paddle 与现有 PyTorch 的运行时及模型内存；
2. 离线网络禁用只作用于解析进程，不改变主业务进程的网络行为；
3. 不创建额外网络服务；模型缓存可由 parser.close 释放；
4. 同一解析器串行提交 CPU 推理，避免线程同时访问同一 Paddle 实例。

原生解析不需要启动子进程。模块 import 不安装依赖、不下载模型、不连接数据库。

## 配置与调用

配置位于 qa_core/document_parsing/config.py；模型根目录默认 models/ocr，正式运行默认 offline=True。下载仅由显式的模型准备脚本完成。

scripts/test_document_parsing.py 提供输入、模式、输出目录、表格开关、耗时与 JSON/Markdown 导出。
模型安装、来源、离线校验、实际测试以 03/04/06 文档的最终记录为准。

## 与业务的边界

解析层不调用 Embedding、不写 PostgreSQL、不执行版本发布。bridge 只在调用者明确批准审核结果后，转换为现有 LegalDocument / SourceLine；入库仍使用原有审核、质量和版本流程。

当前无 FastAPI 入口，因此没有新增上传 API。未来接入实际业务时，沿用其鉴权、资源限额和文件保留策略；不得直接把本地 CLI 包成匿名生产接口。
